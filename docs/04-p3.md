# 04 — P3：先冻结策略，再做低比特扫描

P3 是一次**真实执行**的合成扫描（`rmsnorm` / `softmax` / `layernorm` / `gemv` 四个
`_rsi` 算子，裸金属 Triton/PTX，固定随机数据，不改模型）。它的目标不是打榜，而是
在池内选出“最好的低比特配置”——并且这个选择必须在看到数据之前就定好规则。

## 1. 为什么先冻 `policy.md`

选择规则一旦看过结果再写，就总能挑出好看的那组。所以：

- 规则写进 `p3/policy.md`；
- 它的 sha256 写进 `p3/policy.sha256`；
- `p3/select.py` 在读取池之前先比对哈希，不一致直接退出；
- `selection.json` 内嵌 `policy_version` 与 `policy_sha256`。

改动策略 = 重新冻结 + 提升版本号，旧选择自然失效。

## 2. 规则（按顺序执行）

| 规则 | 内容 |
|---|---|
| **R1 发散否决** | 任一 seed 发散的配置整臂剔除；FP16 对照臂发散则整任务剔除 |
| **R2 精度** | 每任务选平均 `fp16_val_acc` 最高的臂，需满足 `mean ≥ ref - 0.0015`；并列时取总比特更低者，再按配置 id |
| **R3 任务选择** | `best ≥ 全池 FP16 均值 - 0.0035`，且（若有 caveat）`best > caveat + 0.002` |
| **R4 族级** | 按 `mechanism_class` 分组，取选中任务数最多且 ≥ 3 的类；并列按中位增益、再按类名。不足 3 个则退化为任务级并记 `family: null` |
| **R5 联合影响** | 任何组合的口号数字必须是该组合的**实测联合**；分量之和只能作为 planning 估计 |
| **R6 引用** | P1 只能引用 P3 选中的机制类，不能引用论文里的类 |

R3.b 的 caveat 针对“FP16 参照本身就偏弱”的任务：如果参照已经崩了，任何臂都显得“够好”。

## 3. 池的格式

`p3/pool.json`（由 GPU 侧 `p3/measure_pool.py` 生成，当前为 `blocked`）：

```json
{
  "kind": "hgk_p3_pool",
  "device": "NVIDIA H20 96GB",
  "policy_sha256": "…",
  "tasks": [{
    "id": "rmsnorm-b4096-h7168",
    "mechanism_class": "rmsnorm",
    "seeds": [1,2,3,4,5],
    "fp16_val_acc": 0.6123,
    "trials": [{"logical": 3, "bits": {"w": 6}, "seed": 1,
                "fp16_val_acc": 0.6119, "diverged": false, "tok_per_s": 412.5}]
  }],
  "fp16_acc_caveat": {"…": 0.6001},
  "per_class_impact_pct": {"rmsnorm": 1.8},
  "joint": {"mechanisms": ["rmsnorm"], "value": 1.4, "source": "evidence/p3/joint.json"}
}
```

必须存原始 trials，不能只存汇总；否则 R1（发散）与 R2（逐 seed）无法复核。

## 4. 输出

```bash
python3 -m p3.select --pool p3/pool.json --out p3/selection.json
```

`selection.json` 含：策略版本与哈希、池哈希、全池 FP16 均值、每个任务的
`selected / best / reasons[]`（包含被拒原因）、`family`、`selected_mechanisms`、
`joint` 状态、可被 P1 引用的 `p1_mechanism_classes`。

`joint.status` 只有两种取值：`measured`（组合被原样测过）或
`requires_joint_measurement`（此时只给 `planning_sum_pct`，并明确它不是联合值）。

## 5. 当前状态

选择器与策略已在本地实现并测试（`tests/test_p3_select.py`，13 个用例，含策略篡改检测）。
`p3/pool.json` 不存在，也没有生成 `selection.json`。

RTX 6000D 上确实跑过一轮探索性计时：`p3/measure_op_timings.py` 写出了
`p3/evidence/pool_20261115T151201.json` 与 `p3/evidence/pool_20261115T151323.json`
（8 个算子、20 轮、256 MiB L2 flush）。它只测“现有调用 vs 同字节量参考”，
没有低比特臂、没有 `fp16_val_acc`，也不符合池的 schema，因此不能驱动 `p3.select`。
所以现在**没有任何 P3 数字**被写进 README 或判决定论——这是刻意的，
公开数字必须来自可复跑的、注册过的测量。
